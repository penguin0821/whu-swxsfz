# CMS 与演进路线

这份文档讨论网站从现在的"改代码式维护"往"内容可自助更新 + 正式上线"演进的路径。结论先行：**不要一步跳到重型 CMS**。当前单文件静态站的形态非常适合低频、由开发者维护的学术官网；真正该先做的是"数据与视图分离"，它成本最低、收益最大，且为后续任何 CMS 打基础。

---

## 1. 现状与它的边界

现在所有内容（成员、成果、新闻、文案）都硬编码在 `demo6_template.html` 的 JS 数据数组里。更新一条新闻的完整链路是：

改模板 → `python3 reinject6.py` 重新构建 → 部署 `index.html`。

这套流程的优点是极简、零后端、零密钥、产物可离线归档；缺点是**改内容等于改代码**，非技术成员无法自助更新，且每次都要本地构建 + 部署。

**什么时候现状就够用**：更新由懂代码的人做、频率不高（比如每月几条新闻、每年一次成果补充）。对多数课题组官网，这个假设成立。

**什么时候需要引入 CMS**：希望导师/学生不经开发者就能自助发新闻、改成员名单；或更新频率明显上升。

---

## 2. 三条演进路线（由轻到重）

### 路线 A：数据与视图分离（推荐的第一步）

把 `DIRS / SUP / MEM / PUBS / NEWS` 从模板里抽出来，存成 `content/*.json`（如 `content/news.json`、`content/members.json`）。构建时 `reinject6.py` 读取 JSON 注入模板，或页面运行时 `fetch` 加载。

- **收益**：内容与代码解耦。非开发者也能改 JSON（结构清晰、可加校验），不必碰 HTML/JS。仍保持纯静态、零后端、零密钥。
- **成本**：低。一次性重构 + 给构建脚本加读取逻辑。
- **风险**：几乎无。是所有后续方案的地基。
- **建议**：无论最终是否上 CMS，都值得先做这一步。

### 路线 B：Git-based CMS（给静态站加后台）

用 [Decap CMS](https://decapcms.org/)（原 Netlify CMS）这类"无服务器、内容存回 Git"的方案。它在站点上挂一个 `/admin` 后台页面，编辑者在网页表单里改内容，提交后内容以 commit 形式写回仓库，触发重新构建。

- **收益**：非技术成员有了可视化后台；内容仍在自己的 Git 仓库里，无外部数据库、无月费、无厂商锁定。天然适配 GitHub Pages。
- **成本**：中。需配置 `config.yml` 定义内容模型（正好复用路线 A 的 JSON 结构）、接入 GitHub OAuth（用于后台写权限）。
- **风险**：OAuth app 配置、构建触发方式（GitHub Actions）需要一次性搭好。
- **前提**：路线 A 完成后，这一步几乎是"给 JSON 配个表单 UI"。

### 路线 C：Headless CMS（内容托管在外部系统）

用 Notion / Strapi / Contentful / Sanity 等，内容存在外部系统，构建时通过 API 拉取生成静态站（配 GitHub Actions 定时或 webhook 触发）。

- **收益**：编辑体验最好（尤其 Notion，非技术成员零学习成本）；可承载富媒体、多人协作、审批流。
- **成本**：高。引入外部服务依赖、API 密钥管理、构建时网络拉取、可能的费用与限流。
- **风险**：外部服务可用性/策略变动会影响站点更新；密钥泄露面；与"零依赖单文件"的项目哲学有张力。
- **建议**：仅当内容运营复杂度真的上升到需要独立内容平台时才考虑，且谨慎评估。

**推荐顺序**：A（立即做，低风险）→ 视需要 B（要可视化后台时）→ 谨慎评估 C（内容运营变重时）。

## 3. 正式上线：域名、备案、托管

当前 GitHub Pages 适合**预览与内部查看**，作为正式上线还有几件事：

- **域名**：`*.github.io` 不是机构域名。正式上线建议用校方域名下的子路径或独立域名（如 `crcgc.whu.edu.cn`），需要走学校信息化部门的流程。
- **备案**：面向境内公开访问、使用境内服务器/CDN 的站点需 ICP 备案。用校方已备案域名下的子路径通常可沿用学校备案；独立域名需自行备案。**这是正式上线的硬门槛，需尽早与学院/学校信息化部门确认。**
- **可达性**：`github.io` 在中国大陆的可达性存在地区/运营商差异，个别用户可能打不开。正式面向公众应迁到境内托管（对象存储 + CDN，或校方服务器）。
- **托管选项对比**：
  - GitHub Pages：免费、零运维，但境内可达性不稳、非机构域名。适合现在的预览阶段。
  - 对象存储 + CDN（境内）：可达性好、可扩展，需备案、有少量成本与运维。
  - 校方服务器 / 学院统一站群：合规性最好，走学校流程，灵活性受限。

---

## 4. 稳定性与备份

- **Git 历史即备份**：每次内容变更都是一个 commit，可随时回溯。建议每次正式发布打一个 tag（如 `v2026.09`）。
- **单文件可离线归档**：`index.html` 是自包含的，定期把发布版本另存归档，即使托管/仓库出问题也能立刻恢复。
- **构建可复现**：只要仓库在（含 woff2 子集），clone 后 `python3 reinject6.py` 就能重建出同样的产物；引入新汉字时才需要额外下载 OTF。
- **建议的发布纪律**：改模板 → 构建 → 过验收清单（手册第 10 节）→ 部署 → 外网验证 → 打 tag。
